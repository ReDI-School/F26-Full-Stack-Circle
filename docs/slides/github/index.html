First things first

Git is not GitHub

💻

Git

A tool on your computer that saves snapshots of your code (commits) and lets you work on separate branches.

You use it in the terminal or in VS Code.

+
🌍

GitHub

A website that hosts our repository so the whole team can share code, open pull requests and review each other.

Issues and our project board live here too.

The mental model

main is the product. You work on a branch.

Your branch is your own safe copy. Everyone works in parallel. A pull request brings the work back into main.

Nobody commits directly to main. Every change goes through a branch and a pull request.

The big picture

Let's go through each step.

Step 1

📋 Pick an issue

Choose

Pick a ticket from the Todo column of the project board.

Assign

Assign yourself on the issue, so nobody else starts the same work.

Move

Move the card to In Progress. Read the acceptance criteria.

Remember: one ticket in progress at a time, and 7 days max.

Step 2

🌿 Create a branch


# 1. go to main and download the latest changes
git switch main
git pull

# 2. create your branch and switch to it
git switch -c feat/12-login-page

Branch names

type/issue-number-short-name

feat/12-login-pagefix/31-price-roundingdocs/40-api-readmechore/44-update-deps

Why from fresh main?

So you start from the newest code and get fewer conflicts later.

Step 3

💾 Commit small and often


# what did I change?
git status
git diff

# pick the files for the next snapshot
git add frontend/src/app/login/page.tsx

# save the snapshot with a message
git commit -m "feat(frontend): add the login form"

A commit = one small step

That still works on its own. Many small commits > one giant one.

Messages we use

type(scope): what it does

Types: feat fix docs refactor chore. Look at git log for examples.

Step 4

☁️ Push and open a draft PR — on day one


# first push: create the branch on GitHub too
git push -u origin feat/12-login-page

# every push after that
git push

GitHub then shows a "Compare & pull request" button. Click it, choose "Create draft pull request".

Why so early?

  • The team can see your progress
  • Your work is backed up
  • Vercel builds a preview link
  • Someone can take over if needed
Push every day. Nothing should live only on your laptop.

Step 5

🔄 Meanwhile, main moves on

Your branch is now behind main — you don't have your teammates' code. Fix it by merging main into your branch. Do it often, and always before asking for a review.

Step 5

🔄 Bring main into your branch


# 1. save your work first
git status        # nothing uncommitted? good
git switch feat/12-login-page

# 2. download what's new on GitHub
git fetch origin

# 3. merge the latest main into YOUR branch
#    (--no-edit keeps the default message, no editor pops up)
git merge origin/main --no-edit

# 4. send the result to GitHub
git push

✅ No conflicts?

Git makes a merge commit for you. Push and you're done.

⚠️ Conflicts?

Git stops and asks you to decide. Next slide!

We merge, we don't rebase. You can also click "Update branch" on the PR (choose "Update with merge commit") — only when there are no conflicts.

Merge conflicts

😱 A conflict is normal, not an error

It happens when you and someone else changed the same lines. Git can't guess which version is right, so it shows you both:


export function Header() {
<<<<<<< HEAD
  const title = 'Log in to ReDiCycle';
=======
  const title = 'Welcome back';
>>>>>>> origin/main
  return <h1>{title}</h1>;
}

HEAD = your branch's version

origin/main = the version on main

Merge conflicts

🧹 Resolving a conflict, step by step

1
Find the filesgit status lists them under "both modified".
2
Open them in VS CodeUse "Accept Current / Incoming / Both", or the merge editor.
3
Keep the right codeSometimes it's a mix of both. Delete every <<< === >>> line.
4
Check it still worksRun the app and the checks.

# 5. mark the files as resolved
git add frontend/src/components/Header/Header.tsx

# 6. finish the merge (keeps the default message)
git commit --no-edit

# 7. share it
git push
Not sure which version is right? Ask the person who wrote the other change, or pair with someone. Never just delete their code.

Before you ask for a review

✅ Run the checks locally


pnpm lint
pnpm format:check   # or: pnpm format (fixes it)
pnpm typecheck
pnpm build

Why?

A PR can't be merged with broken lint, types or build. Catch it on your machine — it's much faster.

The automatic CI checks on GitHub are not running yet, so the PR checks may stay empty. Right now these local checks are the real gate.

Changed the database schema? See "Before you ask for a review" in CONTRIBUTING.md.

Code review

👀 Reviewing a teammate's PR

Reviews are peer-to-peer — everyone reviews, not just the "seniors". It's the best way to learn the codebase.

📋

1. Read the issue

What should this PR do?

🔗

2. Try it

Open the Vercel preview and click around.

📂

3. Read the code

In the Files changed tab.

💬

4. Comment

Ask, suggest, praise. Then submit.

Asked for a review? Try to do it within a day — someone is waiting on you.

Code review

🤝 Kind and useful comments

😬 Instead of…

"This is wrong."

"Why didn't you use a component?"

"Rename this."

🙂 Try…

"This breaks when the list is empty — could we add a check?"

"We have a Button component — could we reuse it here?"

"nit: data → items reads clearer. Up to you!"

Comment on the code, not the person. Explain why. Ask questions. Use nit: for tiny things. And say when something is good — "Nice, this is really clean!" 🙌
