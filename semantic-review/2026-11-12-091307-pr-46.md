# App shell: navbar, footer, and auth context

This PR wires up the global application frame: `AuthProvider` manages session state via `GET /api/auth/me` on mount, `AppShell` composes `Navbar` + `Footer` around every page, and `RequireAuth` guards five protected routes with cookie-based auth and `?next=&notice=` redirects. No localStorage is used; all fetches go through the existing `api` client with `credentials: 'include'`. The approach is thin and correct for the scope — context carries user state down, the navbar and footer are fed data via `useApi` hooks, and the guarded pages are placeholder shells that will fill in later.

Watch for: `onSearch` signature mismatch between `AppShell` and `Navbar` (**confirmed**); login errors silently swallowed with no user feedback (**confirmed**); `AuthProvider` has no `refresh` call on `login`/`register` — the user object comes from the response body, not a re-fetch, which is fine, but `refresh` itself duplicates `fetchMe` logic without being deduplicated (**confirmed**); duplicate `index.tsx` / `index.ts` in `AppShell/` (**confirmed**); `UseAuth.ts` filename casing is inconsistent with the rest of the codebase (**confirmed**).

**Verdict**: NEEDS_CHANGES

---

## High-level view

`AuthProvider` fetches `/auth/me` on mount and treats 401 as a silent guest state, matching the spec. The `refresh` function is a copy-paste of the mount `fetchMe` — a duplication that will bite if error handling logic ever needs to change.

`AppShell` fires two background `useApi` calls — `/threads` for the unread badge and `/categories` for footer links. The `/threads` endpoint requires auth, so guests get a 401; `useApi` leaves `data` null and `?? 0` zeroes the badge cleanly. The `onSearch` prop passed to `Navbar` ignores the submitted value that `Navbar` passes back and reads local state instead — compatible at runtime but diverges from the contract.

`RequireAuth` redirects guests to `/login?next=...&notice=...` and non-admins to `/`. The open-redirect guard is sufficient because `pathname` comes from `usePathname()`, which only returns the pathname portion.

The login form catches errors from `login()` with `console.error` and no user-visible message — a user who types the wrong password gets no feedback at all.

`AppShell/` ships both `index.tsx` and `index.ts`. Bundler resolution between them is not guaranteed to be stable; the `.tsx` is a stale artifact. `UseAuth.ts` is named in PascalCase while the rest of the hooks use camelCase, and it's imported directly in two files instead of via the barrel.

No tests for `AuthProvider`, `RequireAuth`, or the login redirect flow ship with this PR. The Playwright browser project added to `vitest.config.ts` has the right globs to cover them.

### `onSearch` callback ignores submitted value

`Navbar.types.ts` declares `onSearch?: (value: string) => void` — the Navbar calls this with the text that was submitted (on Enter or mobile "Go"). `AppShell` wires it as:

```ts
const handleSearch = () => {
  router.push(`/?q=${encodeURIComponent(searchValue)}`);
};
```

`handleSearch` has no parameters, so the value Navbar passes is thrown away and the component reads its own `searchValue` state instead. The two are kept in sync via `onSearchChange`, so today this works. But if Navbar ever submits a normalised or trimmed version of the input (e.g. collapsing whitespace), the query string will silently use the un-normalised state value. Fix: `const handleSearch = (value: string) => router.push(`/?q=${encodeURIComponent(value)}`)`.

### Login error swallowing

```ts
onClick={async () => {
  try {
    await login(email, password);
    // ...
  } catch (error) {
    console.error('Login failed:', error);
  }
}}
```

`api.post` throws an `ApiError` with `error.message` set to the server's human-readable message on a 401 or 422. The catch block discards it. A user who types the wrong password gets no feedback. Add an error state piece to `LoginForm` and render `error.message` below the submit button.

### Network failure during `/auth/me` triggers spurious redirect

A transient error (DNS timeout, proxy 503) during app startup hits the non-401 branch, which sets `user` to null and `loading` to false. `RequireAuth` then treats that null as "guest" and redirects to login. This is likely not intentional — a startup network blip should probably hold the loading state or surface an error rather than drop the user to the login page. Worth a team decision before guarded routes go live.

### `refresh` / `fetchMe` duplication

`fetchMe` inside the `useEffect` and `refresh` are structurally identical. The only difference is `refresh` calls `setLoading(true)` first (unnecessary on mount since `loading` starts `true`). A single extracted `syncUser` function would ensure any future change to error handling — adding a retry, changing the non-401 fallback — only needs to happen in one place.

### Admin route distinction leaks existence

Non-admins hitting `/admin` are redirected home; hitting any truly non-existent route would 404. That difference lets a non-admin probe whether `/admin` exists. If information leakage is a concern, serve a 404 instead of `router.replace('/')`.

### Missing test coverage

The vitest `hooks` project covers `src/hooks/**/*.test.tsx` and `src/app/**/*.test.tsx` — the right globs, but no test files exist in those paths for this feature. Minimum cases worth adding before guarded routes carry real data:
- `AuthProvider` on mount: 200 sets user, 401 silently sets user=null, non-401 network error also sets user=null.
- `RequireAuth`: `loading=true` renders nothing; `user=null` calls `router.replace`; non-admin with `needAdminRights` redirects to `/`; admin with `needAdminRights` renders children.
- Login form: `?next=/account` redirects there after success; `?next=//evil.com` is sanitised to `/`.
